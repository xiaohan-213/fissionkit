# Contributing

Contributions are welcome, particularly new splitting recipes (generalized
thinning families) and applied workflows.

The bar for a new splitting recipe is the statistical contract, not just code
review: add property tests in the style of tests/test_thinning_properties.py
demonstrating by seeded simulation that (i) folds recombine to the input,
(ii) marginal laws match the theory (KS / chi-square), and (iii) folds are
independent. Applied recipes must additionally test their scientific claim
(error control, coverage, or oracle consistency).

Run `python -m pytest tests/` before opening a pull request; CI runs the same
suite on Python 3.9-3.13 across Linux, macOS and Windows, plus lint and
packaging checks.

Any number quoted in a docstring, the README or the manuscript must be
regenerated by a script under `examples/`; `paper/versions.txt` maps every
quoted number to its script.

Any interpreter or dependency version claimed in `pyproject.toml`, the README
or the manuscript must have been run, not merely configured. Before a release,
run the suite on every supported interpreter and at the declared minimum
dependency versions; `uv` makes this a few minutes' work:

```bash
for v in 3.9 3.10 3.11 3.12 3.13; do
  uv venv --python $v /tmp/fk-$v && uv pip install --python /tmp/fk-$v/bin/python -e ".[dev]"
  PYTHONPATH=src /tmp/fk-$v/bin/python -m pytest tests/ -q
  /tmp/fk-$v/bin/python -m mypy src/fissionkit
done
uv venv --python 3.9 /tmp/fk-min && uv pip install --python /tmp/fk-min/bin/python \
  "numpy==1.22.4" "scipy==1.8.1" "scikit-learn==1.1.3" pytest mypy
PYTHONPATH=src /tmp/fk-min/bin/python -m pytest tests/ -q
/tmp/fk-min/bin/python -m mypy src/fissionkit
rm -rf src/*.egg-info   # left by the editable installs; with it present the
                        # installed-metadata test runs instead of skipping
```

Expect "108 passed, 1 skipped" from a clean tree (the skipped test compares
`__version__` with installed metadata and is exercised by `release.sh`), or
"103 passed" if an install is visible. Record the outcome in
`paper/versions.txt`. Releases 0.1.7-0.1.11 shipped PEP 604 signatures, so
the annotation tests added in 0.1.8 could not have passed on Python 3.9, and
no release before 0.1.12 records a run outside the reference environment:
the matrix had been written into CI but not run.

## Tools that CI installs at "latest"

Every CI step that installs an unpinned tool or dependency (`ruff`, `mypy`,
`numpy` in the typecheck job) must have been run locally at the version pip
resolves *today* before the release, and that version recorded in
`paper/versions.txt`. Three releases in a row were caught by exactly this:
0.1.12 by ruff's default rule set rewriting `Optional[X]` back to `X | None`,
0.1.13 by NumPy 2.5 changing `typing.get_origin(NDArray[...])`, and 0.1.14 by
NumPy 2.5 typing `ndarray.mean()` precisely enough for mypy to reject an
assignment that NumPy 2.4 had typed as `Any`. Each job was green in the
reference environment and red at the version CI would actually install.

## Statements about other software

Any sentence in the manuscript, README or docstrings that characterises a
third-party package must point at a specific file in that package's
repository, checked on the date given in the citation. "Only mean-level
tests" was written about the datathin Python port and was wrong: its
`datathin/test_helpers.py` holds 55 test functions asserting mean, variance
and correlation thresholds. What it lacks - distributional tests, joint
independence tests, error-control tests - is what fissionkit adds, and that
is what the manuscript now says.

## Public signatures

`tests/test_api_signature.py` snapshots the name, kind and default of every
parameter of every public callable. Bit-identity tests pin what functions
return; the snapshot pins what they accept. Changing a signature means
updating the snapshot in the same commit and describing the change in
CHANGELOG.md as affecting existing calls. Recipe options are keyword-only;
keep them so. Before a release, also diff the snapshot against the previous
release archive.

## Tools that write user data into another syntax

Every place where a value from the user crosses into another syntax is a
boundary that needs its own test case with that syntax's metacharacters:
TOML strings, YAML scalars, XML text, and - easy to forget - the replacement
argument of `re.sub`, which re-interprets backslashes. `fill_placeholders.py`
crossed all four; 0.1.23 got YAML wrong and 0.1.24 got `re.sub` wrong, each
caught by the next audit's probes rather than by the tool's own self-test.
Use callable replacements, quote scalars with `json.dumps`, escape XML
text, validate every written file, and sample the *claimed* input domain
in the self-test - its content (metacharacters), its form (URL prefixes,
missing fields) and its *type*: JSON `"no"` is a truthy string, and a
syntax validator cannot see that an author flagged `"no"` was written as
corresponding. Only a semantic assertion in the self-test can. And the
input domain includes every command that appears in the documentation,
run verbatim: `--apply paper/submission.example.json` filled a tree with
fictitious authors until 0.1.27 refused the example file.

## Validators

A validator is only as good as the inputs it was tried on. Before changing
one, probe it on the product of four dimensions and require the same verdict
along every axis where the answer should not change:

1. precision - the input computed in float32 and in float64;
2. structure - full-rank and rank-deficient (p > n);
3. scale - the same matrix times 1e-9, 1 and 1e6 (the units of the data);
4. symmetry - exact, float-level asymmetric, and grossly asymmetric.

Tolerances must be relative to the scale of the input (`max|Sigma|`, the
largest eigenvalue) unless the property being tested is genuinely absolute
(whether a count is an integer). `np.allclose` with its default `atol`, and
`max(1.0, ...)` floors, are both absolute and both shipped in a validator
between 0.1.11 and 0.1.13; a covariance in the data's own small units passed
grossly indefinite. `tests/test_v0114_fixes.py` is the template.

## Before the first public tag

Everything below is owned by the authors, not by the release checks:

1. Replace every placeholder: `pyproject.toml` (authors, URLs), `LICENSE`
   (copyright line), `CITATION.cff` (authors, repository), `README.md`
   (install URL) and in the manuscript the author block, Table 1 C2/C9,
   Table 2 S2/S8, CRediT, competing interests, funding and the AI statement.
   Copy `paper/submission.example.json` to `paper/submission.json`, fill it
   in (remove the `_comment` key), and run `python scripts/fill_placeholders.py
   --apply paper/submission.json`; the example file itself, or any value
   left over from it (`example.org` addresses, the zero DOI or ORCID), is
   refused. It writes all five files from that one source,
   validates each written file (TOML parse, CITATION.cff via cffconvert or
   PyYAML or a structural scan, well-formed document XML) and re-checks that
   nothing is left (`--check` lists what remains at any time; `--self-test`
   rejects nine malformed submissions - the example file itself and wrong
   JSON types included - and applies ten, including names and affiliations
   with backslashes, `\1`, `:`, `&`, `<` and non-ASCII letters, ORCID/DOI
   given as URLs, values with surrounding whitespace and an affiliation
   spelled two ways). Open the manuscript once afterwards.
2. Decide the public version. The changelog records a run of same-day patch
   releases from 0.1.11 onward (count the dates in `CHANGELOG.md`) because
   each audit round shipped as a release; a reader of the repository will
   not know that. Either keep the history as
   it is, or squash it into a single `0.2.0` before the first push, and cite
   that tag in Table 1, Table 2 and `CITATION.cff`.
3. Push, and read the CI results for macOS and Windows: no release has been
   run on either. Update the sentence in manuscript §2.1 that says the
   matrix was run locally on Linux.
4. Publish to PyPI (Table 2 S2), mint the Zenodo DOI for the tag (Table 1
   C2), and record the library versions of that build in
   `paper/versions.txt`.

## Verification discipline

A stale editable install once redirected imports to an old copy of the
package, so measurements were taken on code that was not the code under
test. To prevent a recurrence:

1. Before trusting any measurement, assert the import path:
   `python -c "import fissionkit, inspect; print(inspect.getfile(fissionkit))"`.
   The test suite enforces this automatically (tests/conftest.py).
2. Cold-start verification uses PYTHONPATH isolation, never a global
   editable install from a sandbox.
3. Releases go through scripts/release.sh, which has two modes. Cutting a
   release (HEAD not yet tagged `v<version>`): the top `CHANGELOG.md` entry
   must name the package version, and it and `CITATION.cff` `date-released`
   must both carry today's UTC date (both files use UTC dates). Verifying a
   release that exists (HEAD tagged `v<version>`, or `--verify`): the two
   files must agree with each other, and their date is the release date,
   not today's. Either way it then rebuilds the archive from HEAD and
   re-runs the full suite from that archive in a fresh directory.
   Two further checks belong to every release: `python scripts/check_wheel.py
   dist/*.whl src/fissionkit` (the wheel ships exactly the tested tree; CI
   runs it too), and, for a release that claims to change only
   documentation, `python scripts/bytecode_diff.py <previous>/src src` (nothing that
   determines behaviour changed: it fingerprints every module's whole
   code-object tree after stripping docstrings, so module-level statements,
   closures, defaults, constants, `__all__`, strings and annotations are all
   inside it; only docstrings, comments, blank lines, line numbers and the
   `__version__` string are ignored. `--self-test src` applies nine
   mutations that must be detected and five that must not; run it whenever
   the script itself is touched. It needs no dependencies). Run the examples from the built
   archive as well; a signature or calling-convention change touches every
   caller and the test suite does not import the example scripts.
4. If a code change leaves a measured number suspiciously unchanged, first
   suspect that the new code was never executed.
5. Any check that compares something to "now" must be asked what it means
   for yesterday's artefact. Probe it by putting a fake `date` (returning
   tomorrow) on `PATH` and running the check against a released tree: a
   release must stay verifiable after its day. 0.1.28's date check refused
   every released archive from the next UTC day on.
6. Exit-code checks must not be taken through a pipe (`cmd | tail; echo $?`
   reports the pipe's last command). Capture the exit status directly.
